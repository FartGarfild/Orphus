# Orphus AV Scanner

Самодостатній антивірусний сканер на bash для Linux-серверів (перш за все — shared/VPS-хостинг з PHP-сайтами). Один файл, ~6000 рядків. `--setup` самостійно ставить компілятор і збирає весь потрібний тулчейн з вихідного коду — не покладається на те, що система вже має щось готове.

## Чому не просто ClamAV

ClamAV, будучи чудовим рушієм, індексує мільйони сигнатур наперед у структурах для швидкого пошуку — і платить за це гігабайтом+ оперативної пам'яті, що на бюджетному VPS часто просто неприйнятно. Oprhus іде іншим шляхом: плоскі файли сигнатур + пакетний `grep`/YARA-пошук замість попередньої індексації сигнатур у пам'яті. На порядок економніше по пам'яті, і власний інкрементальний кеш файлів (`-I`, дисковий, не в ОЗУ) дає той самий ефект прискорення повторних сканів того самого дерева, що й індексація — просто на іншому рівні (файли, не сигнатури).

## Джерела сигнатур

Скрипт не вигадує власну базу — він споживає й об'єднує:
- **ClamAV** (`main.cvd` + `daily.cvd`) — підтверджено ~99.98% реального покриття сигнатур офіційної бази
- **Maldet/LMD** (`rfxn.*`) — hdb/ndb/ldb/yara формати
- Довільні зовнішні **YARA**-репозиторії
- Власні **custom**-сигнатури (hash/string)

Разом — понад 3.6 мільйони сигнатур з коробки після `--update`.

## Продуктивність

- Пакетна обробка hash/YARA-перевірок (не один процес на файл)
- **Індексація файлів на диску** (`-I`) — маніфест раніше просканованих чистих файлів (mtime+розмір), пропускає незмінені при повторному скані того самого дерева. Не в ОЗУ, як у ClamAV з сигнатурами, а на диску — але той самий принцип "не робити роботу двічі"
- `--sig-in-ram` — база сигнатур у `/dev/shm`, гарантований RAM-хіт замість надії на page cache
- RAM-стеля з автоматичним підбором воркерів під низькоресурсні системи
- **~130-170 файлів/сек** на реальному навантаженні (перевірено на повному скані `/` з 136K+ файлів)

## Режими роботи

| Прапорець | Що робить |
|---|---|
| (за замовчуванням) | Швидкий одноразовий скан, автоматичне придушення відомих хибних спрацювань |
| `-w`, `--real-time` | Фоновий демон, inotify (миттєва реакція) з fallback на polling |
| `--deep` / `--paranoid` | Максимальна прискіпливість: обходить **усі** автоматичні придушення, вмикає SUID-верифікацію й сканування архівів, піднімає ліміт розміру файлу до 200MB |
| `-A`, `--scan-archives` | Розпакування й сканування вмісту zip/tar/7z/rar, з захистом від decompression bomb у реальному часі |
| `-P`, `--scan-processes` | Виявлення процесів з видаленим backing-файлом, LD_PRELOAD-ін'єкцій, розбіжностей `/proc` проти `ps` |
| `-K`, `--check-kernel` + `--offline-root` | Перевірка цілісності ядра/завантажувальних файлів проти контрольних сум пакетного менеджера — призначено для запуску з rescue-режиму провайдера проти змонтованого (не завантаженого) диска |
| `-q`, `--quarantine` | Карантин з маніфестом для відновлення; `--quarantine-dry-run` показує що було б зроблено без реальних змін |

## Точність — менше хибних спрацювань, ніж здається

- **Вендор-фінгерпринти**: розпізнає обфускацію легітимних CMS (перевірено на DataLife Engine) за вмістом файлу, не за шляхом — придушує лише там, де є справжній технічний підпис вендора, залишаючи те саме YARA-правило активним будь-де ще
- `ignore_sigs` — точкові виключення за шаблоном (тип+шлях), з активними за замовчуванням записами для типових системних хибних спрацювань (`chroot`, `nc`)
- SUID/SGID-звіт **окремо** від основного (не тоне серед десятків стандартних системних бінарників)
- `--deep` навмисно ігнорує всі ці придушення — коли треба бачити геть усе

## Портативність і стійкість середовища

Здатен запуститись майже будь-де, маючи лише файлову систему й ядро:
- Busybox-first: власний статичний busybox, з автозавантаженням і fallback на системні інструменти
- `--setup` **сам ставить компілятор і build-залежності** (`gcc`, `make`, `autoconf`, `pkg-config` тощо) через apt/dnf/yum/zypper/pacman/apk — залежно від того, яка система, і компілює `grep`/YARA/`bash` з вихідного коду, якщо системні варіанти биті чи відсутні
- Самокомпільований `bash` + `re-exec` на старті — звужує вікно довіри до потенційно скомпрометованого системного інтерпретатора

## Безпека самого інструмента

Оскільки сканер зазвичай працює під root:
- Розпакування архівів у пісочниці (`bwrap`/`unshare`/`chroot`/`simple`, автовибір найкращого доступного) — за замовчуванням увімкнено
- Захист від zip-slip/symlink-escape, перевірено прямими тестами шкідливих архівів
- Явна перевірка `mountpoint -q` перед будь-яким `rm -rf` у chroot-пісочниці — не видаляє нічого, поки монтування активне
- Обмеження розміру й перевірка завантажених бінарників (ELF-магічні байти, а не лише текстовий вивід)
- Виявлення файлів з аномальними (керуючими символами) іменами — техніка ухилення від виявлення
- Self-exclusion — не сканує власну інсталяцію й тимчасові файли

## Діагностика

`Time breakdown` (hash/YARA/PE-секції окремо), `-L`/`--long-time` лог повільних пакетів, живий потоковий звіт (`-o`) що переживає переривання скану.

## Встановлення

```bash
git clone <repo> && cd <repo>
./av.sh --setup          # компіляція grep/yara/bash з джерела
./av.sh -u                # завантаження баз сигнатур
./av.sh -d /home           # перший скан
```

## Приклади

```bash
./av.sh -d / --deep -o result.log              # повний, максимально прискіпливий аудит
./av.sh -w -q                                   # фоновий моніторинг з карантином
./av.sh -P                                      # лише перевірка процесів, без файлового скану
./av.sh --offline-root /mnt/rescue -K -d /mnt/rescue   # перевірка ядра з rescue-режиму
```

## Обмеження, чесно

- Не заміна ClamAV щодо ширини покриття складних форматів (байткод-детекція, розпаковування пакерів) — свідомий компроміс заради економії ОЗУ
- `-P`/процесний модуль ловить прості userspace-техніки; не бачить крізь справжній ядровий (LKM) руткіт — це поза можливостями будь-якого userspace-інструменту без офлайн-аналізу
- Аудит безпеки — процес, не одноразова подія; знайдені й виправлені класи вразливостей задокументовані в історії комітів, але повнота не гарантована

##
Файл ignore_sigs достатньо скопіювати в директорію signatures після її створення, після чого при звичайному режимі система автоматично буде враховувати ці виключення.
